# Командный проект. Модуль 2 — первая версия ML-сервиса

**Что нужно получить:** обученную модель **v1**, работающий HTTP-сервис в Docker, проверки качества и производительности и понятное решение: можно ли выпускать эту версию. Это первая часть одного проекта, который продолжится в [модуле 3](project-m3.md).

**Когда:** задания `Z01–Z05`, затем защита `EK1` в учебный день `Д06`. Точный срок сдачи — на учебной платформе. Работаете командой **4–5 человек**.

**Какой результат ожидается:**

```text
Данные → обучение v1 → HTTP-сервис в Docker
             │                  │
     проверка качества    проверка API и нагрузки
             └────────┬─────────┘
              решение о выпуске
```

К первой защите всё на схеме должно быть воспроизводимо из вашего репозитория.

## 1. Начало работы: команда, тема и данные

Сначала соберите команду, выберите [тему](topics.md) или предложите свою, создайте **один закрытый GitHub-репозиторий** и добавьте преподавателя и ассистентов. В `Z01` сдаётся короткая заявка: участники, задача, ссылка на датасет, предполагаемая метрика качества и **самая дорогая ошибка модели** (например, опасный пропуск неисправности). На этом шаге писать сервис ещё не нужно.

Требования к данным:

- Открытый набор табличных данных или коротких текстов: **от 5000 записей, исходный файл до 200 МБ**. Лицензия разрешает учебное использование; персональных данных быть не должно.
- Есть поле времени, источника или устойчивого сегмента, чтобы сравнивать группы объектов и моделировать изменения данных.
- Данные делятся примерно **60% / 20% / 20%**: обучение, отложенная проверка, резерв эксплуатации. Если есть время — делите по хронологии. Записи одного клиента, устройства или другого объекта не должны оказаться в разных частях.
- Резерв содержит **минимум 1000 записей**. Но одного количества недостаточно: ещё при выборе данных проверьте, что из резерва реально можно сделать **три неповторяющихся пакета минимум по 300 записей**, включая один со сдвигом доли источника/сегмента в 1,5 раза или распределения признака. Для предварительной проверки достаточно подсчитать количество записей по источникам/сегментам, **не просматривая признаки и метки отдельных объектов**. Если это невозможно — согласуйте другой датасет или разбиение. **До модуля 3 резерв не используем для анализа и обучения**.
- Модель, признаки и предобработка настраиваются только на обучающей части. Для выбора алгоритма и гиперпараметров можно выделить **внутреннюю валидацию из обучающих 60%**. Отложенные 20% используют для независимой приёмки: **до первого запуска на них нужно зафиксировать метрику, срезы и пороги**. Не подбирайте параметры и не меняйте пороги по результатам на отложенной выборке.

В репозиторий кладите **скрипт получения и разбиения данных**, ссылку на источник и контрольную сумму исходного файла. Сами датасеты загружать в GitHub не нужно.

## 2. Что должно работать к первой защите

**Обучение модели v1.** Команда сама обучает простую модель классификации или регрессии, сохраняет модель вместе с предобработкой и фиксирует параметры обучения. Другой человек должен суметь повторить обучение по `README.md`. Обучение занимает **не больше 10 минут** на ноутбуке с 4-ядерным CPU и 8 ГБ оперативной памяти, без GPU.

**HTTP-сервис.** Сервис принимает запрос с признаками, проверяет вход и возвращает предсказание. В ответе можно определить версии модели, кода и обучающих данных. У каждого запроса есть `request_id`: сервис возвращает переданный идентификатор или создаёт его сам. Нужны понятные ответы на ошибочные запросы, проверка готовности сервиса и запасной ответ **там, где он уместен для вашей задачи**. Сервис запускается в Docker и использует не более **2 ГБ памяти**.

Например, ответ регрессионного сервиса может выглядеть так (поля и значения учебные):

```json
{
  "request_id": "req-001",
  "prediction": 18.6,
  "model_version": "v1",
  "code_version": "c1",
  "data_version": "d1",
  "fallback_used": false
}
```

У классификатора вместо числа может быть название класса. Оценка уверенности необязательна: она есть не у каждой модели. Имена HTTP-маршрутов и используемые библиотеки команда выбирает самостоятельно.

**Проверки качества.** Нужно подготовить условия, по которым можно принять или отклонить модель:

- одну основную метрику, связанную с задачей и ценой ошибки;
- простую **базовую модель** для сравнения и числовой порог относительно неё;
- качество минимум на **двух срезах** данных (например, по источникам или сегментам) и ограничения для важных срезов;
- минимум **три автоматических поведенческих теста** (например, реакция на очевидный пример или изменение несущественного поля).

Условия приёмки фиксируются **до первой оценки кандидата на отложенной выборке**. На этапе `Z02` можно обучить v1, но её независимую проверку проведите только после фиксации критериев в `Z03`. Проверки должны запускаться командой из репозитория. Высокая средняя метрика сама по себе не означает, что модель готова.

**Если v1 не прошла приёмку, это допустимый результат:** зафиксируйте отказ от выпуска и причины. Рабочий сервис, корректные проверки и измерения всё равно нужны для защиты. В следующем модуле v1 будет использоваться как учебная исходная версия, даже если её промышленный выпуск не был бы разрешён.

**Проверки сервиса.** Нужен автоматический тест, сравнивающий ответы модели и HTTP-сервиса хотя бы на **20 одинаковых входах**. Проверяйте также некорректные типы, отсутствующие поля, недопустимые значения и выбранные запасные реакции. Числовые результаты сравнивайте с разумным допуском к округлению.

**Нагрузка.** Проведите измерения **при трёх уровнях нагрузки**. Зафиксируйте условия опыта, медиану задержки (**p50**), 95-й перцентиль (**p95**), ошибки и вывод: при какой измеренной нагрузке сервис укладывается в выбранный бюджет. Для этого достаточно локального генератора запросов.

## 3. В каком порядке делать

- `Z01` — команда, тема, датасет, репозиторий и заявка.
- `Z02` — модель v1, воспроизводимое обучение, Docker/HTTP-сервис и тест совпадения.
- `Z03` — метрика, базовая модель, срезы, условия приёмки и поведенческие тесты.
- `Z04` — проверки входа, ошибки и запасные реакции.
- `Z05` — нагрузочные измерения, итоговая проверка и подготовка первой защиты.

Конкретные инструкции к каждому шагу появятся в [`assignments/`](assignments/README.md). Они уточняют работу, но не заменяют требования на этой странице.

## 4. Репозиторий и сдача

Рекомендуемая структура (можно назвать папки иначе):

```text
README.md       как получить данные, обучить модель, запустить сервис и тесты
data/           загрузка и разбиение данных
training/       обучение и сохранение модели
service/        HTTP API и Docker
tests/          тест совпадения, приёмка и проверки входа
experiments/    нагрузочный сценарий и результаты
docs/           контракт API, критерии и решение о выпуске
```

К `EK1` в репозитории должны быть **работающий код, тесты, результаты измерений и короткое решение «выпускать v1 или нет»**: на каких числах основано решение, какие риски остаются. Подготовьте **один слайд** с главными результатами.

Сдача фиксируется Git-тегом **`z5`**. Проверяется состояние репозитория, на которое указывает тег, в установленный на учебной платформе срок. **Промежуточные задания не требуют отдельных тегов**: их результаты видны в истории репозитория. Дополнительная демонстрация не заменяет воспроизводимый проект.

## 5. Личный вклад, сложность и оценка

Обязательных ролей нет: распределите работу как вам удобнее. Каждый участник делает полезные изменения **со своей учётной записи GitHub**. Учитывается содержание коммитов — код, тесты, эксперименты и документация, а не их число. На защите **каждый** объясняет собственную работу и принятые решения. Генеративный ИИ разрешён; коммиты с кодом, подготовленным с его помощью, помечайте `[ai]`.

Ориентир самостоятельной работы — **около 18 часов на студента** в модуле 2, но это предварительная оценка, а не ограничение и не требование отработать часы. В команде из четырёх нагрузка может быть выше. Работу можно разделить по направлениям: данные и модель, API и контейнер, тесты и приёмка, нагрузочные эксперименты и интеграция — без жёсткого закрепления ролей.

За защиту `EK1`: **до 6 баллов** за общий результат команды, **до 2** за подтверждённый личный вклад и **до 2** за личный ответ. Шесть командных баллов распределяются так: **до 2** — сервис и контракт, **до 2** — приёмка модели, **до 2** — проверки входа и нагрузка. Оценивается качество реализации и обоснованность решения, **а не обязательное достижение высокой точности**. Если студент совсем не может объяснить свою работу, оценка за защиту ограничивается **4 баллами**. В `EK2` проводится отдельная индивидуальная письменная работа без ИИ и чужой помощи.

**Не требуется:** сложная нейросеть, рекордная точность, графический интерфейс, облачный сервис, Kubernetes, промышленная MLOps-платформа, автоматическое переобучение или полноценная система мониторинга. Эти задачи не являются целью первого модуля.
